# AlertIQ

**Risk-constrained reinforcement learning for adaptive AML alert governance.**

AlertIQ is an end-to-end AI system for Anti-Money-Laundering (AML) alert
triage in banking. It combines a rule-based monitoring layer, a calibrated
fraud-risk model, a reinforcement-learning decision policy, drift/safety
monitoring, an explainability engine, a FastAPI backend, and a React
dashboard — with one goal: **cut the false-positive workload that buries
compliance analysts, without letting a single extra fraud case through.**

> Every metric quoted below comes from `outputs/rl_outputs/evaluation_report.txt`
> and the charts in `outputs/`, generated by running this project's own
> pipeline against the full 6.36M-row PaySim dataset. Nothing here is a
> projection.

## Problem Statement

AML monitoring systems are deliberately over-sensitive — missing a real
fraud case is far more costly (regulatory, financial, reputational) than
reviewing one extra benign transaction. That safety-first posture has a
predictable side effect: **alert fatigue**. Analysts spend nearly all their
time dismissing false positives, real fraud gets buried in the noise, and
review quality drops as volume rises.

On the full PaySim dataset, AlertIQ's own rule engine reproduces this
problem before solving it:

| Metric | Value |
| --- | --- |
| Raw transactions | 6,362,620 |
| Rule-based alerts generated | 2,050,000+ |
| Fraud captured by rules | 96.48% |
| Analyst reviews required (pre-AI) | 2M+ |

That's the starting point: a rule layer tuned for near-total recall,
generating a workload no human team can sustainably review.

## Approach

AlertIQ treats alert governance as a **decision problem**, not just a
classification problem. Three layers work together:

1. A **calibrated ML model** estimates the true fraud probability of each
   already-flagged alert (the rules over-alert on purpose; the model's job
   is to separate signal from noise within that alert pool).
2. A **reinforcement-learning policy** learns *when* to suppress a
   low-risk alert versus escalate it, under an asymmetric reward that makes
   missing fraud far more costly than any workload savings.
3. A **drift detector** watches for the model's world changing under it,
   and forces conservative behavior (escalate more, suppress less) the
   moment it does.

Every decision the system makes is paired with a human-readable
explanation, because in AML compliance, "the model said so" is not an
acceptable audit trail.

## The 5-Phase Pipeline

**Phase 1 — Data and rules.** Load PaySim transactions, engineer
AML-relevant features (transaction bursts, balance-drain ratios, type
encoding), and apply four interpretable rules to generate the initial
alert pool. This is the "legacy system" baseline: high recall, terrible
precision, by design.

**Phase 2 — ML suppression.** Train a cost-sensitive logistic regression
(50:1 penalty for missing fraud) wrapped in Platt-scaling calibration, so
its output isn't just a ranking but a genuinely interpretable probability
— required for the RL state space and for audit explanations downstream.

**Phase 3 — RL optimization.** Model alert governance as a sequential
decision problem. A Deep Q-Network learns a suppress/escalate policy under
an asymmetric reward (see [RL Formulation](#rl-formulation)), trained with
balanced experience replay so the ~0.1% fraud rate doesn't starve learning.
It's benchmarked against a family of static thresholds and a contextual
bandit baseline.

**Phase 4 — Drift and safety.** Continuously compare incoming data's
distribution against the training distribution using PSI and KL
divergence. On critical drift, the system automatically biases toward
escalation rather than trusting a model that may no longer reflect
reality — see `examples/02_drift_detection_demo.py` for this in action.

**Phase 5 — API and deployment.** Serve every decision — with its
explanation — through FastAPI, and surface live metrics, drift status, and
policy comparisons through a React dashboard.

## System Components

| Layer | What it does | Source |
| --- | --- | --- |
| Rule engine | Generates AML alerts from high-value, burst, risky-type, and balance-drain rules | `src/alert_rules.py` |
| Analyst simulator | Creates labeled analyst feedback with junior/senior trust scoring | `src/analyst_simulator.py` |
| Suppression model | Produces calibrated `prob_fraud` values for the decision layer | `src/suppression_model.py` |
| Threshold evaluator | Benchmarks static gating thresholds from 0.50 to 0.99 | `src/gating_evaluator.py` |
| RL environment | Models alert governance as suppress/escalate decisions with asymmetric costs | `src/rl_environment.py` |
| DQN agent | Learns adaptive suppression policy using replay and target network stabilization | `src/rl_agent.py` |
| Drift detector | Tracks PSI and KL divergence for safety monitoring | `src/drift_detector.py` |
| Explainability engine | Produces audit-readable decision explanations | `src/explainability.py` |
| FastAPI backend | Serves evaluation, drift, model, and pipeline endpoints | `api/` |
| React dashboard | Displays live metrics, charts, research flow, and model status | `frontend/` |

## Getting Started

### Prerequisites

- Python 3.10+
- Node.js 18+ (for the frontend)
- ~2 GB free disk space if you download the full PaySim dataset

### Backend setup

```bash
git clone <this-repository-url>
cd AlertIQ

python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

### Dataset setup

For a **quick look** at the system, you don't need to do anything extra —
`dataset/sample_paysim.csv` is already included and every example script
uses it automatically.

To reproduce the **actual reported metrics**, download the full dataset:

```bash
# 1. Download PS_20174392719_1491204439457_log.csv from
#    https://www.kaggle.com/datasets/ealaxi/paysim1
# 2. Place it at:
mkdir -p data
mv ~/Downloads/PS_20174392719_1491204439457_log.csv data/PaySim.csv
```

See [`dataset/README.md`](dataset/README.md) for the full schema and more detail.

### Run the full pipeline

```bash
python run_all.py
```

Or run phases individually (useful for debugging or re-running just one stage):

```bash
python run_eda.py
python run_phase2.py
python run_phase3.py
python run_phase4_rl.py
python run_phase5_drift.py
```

### Start the API

```bash
python -m uvicorn api.main:app --reload --port 8000
```

Open the interactive docs at [http://localhost:8000/docs](http://localhost:8000/docs).
The API starts fine even without a trained model — it falls back to a
static-threshold decision and a neutral 0.5 probability until you've run
the pipeline (see [API Reference](#api-reference)).

### Start the frontend

```bash
cd frontend
npm install
npm run dev
```

The Vite dev server prints the local dashboard URL, usually
[http://localhost:5173](http://localhost:5173).

## Running the Tests

```bash
pip install -r requirements-dev.txt
pytest
```

32 tests, running in well under a second, with **no dataset download and
no trained model required** — everything runs against the synthetic
sample in `dataset/` and in-memory fixtures. Coverage includes:

| File | What it checks |
| --- | --- |
| `tests/test_alert_rules.py` | Rule engine output shape, high-value threshold logic, fraud recall on realistic data |
| `tests/test_drift_detector.py` | PSI/KL correctness on identical vs. shifted distributions, fallback bias activation |
| `tests/test_rl_environment.py` | Asymmetric reward values match `src/config.py`, episode bookkeeping, balanced sampling, the adaptive-threshold baseline policy |
| `tests/test_explainability.py` | Risk classification, template selection, drift-override explanations |
| `tests/test_config.py` | Safety invariants — e.g. the missed-fraud penalty must always dominate every other reward |
| `tests/test_api.py` | FastAPI endpoints respond correctly in cold-start (no model loaded) mode |

## RL Formulation

| Component | Definition |
| --- | --- |
| State | `[prob_fraud, rule_count_norm, amount_norm, fraud_rate, workload_level]` |
| Actions | `0 = SUPPRESS`, `1 = ESCALATE` |
| Reward | Suppress fraud: `-500`, suppress benign: `+1`, escalate fraud: `+5`, escalate benign: `-0.5` (values as configured in `src/config.py`; the asymmetry — missing fraud is penalized far more than anything else is rewarded — is the property that matters, not the exact numbers) |
| Objective | Maximize cumulative reward while preserving high fraud recall |

## Limitations & Future Work

Being upfront about scope, since these matter as much as the results:

- **Simulated data.** PaySim is a well-regarded fraud-research simulator,
  but it is still synthetic. Real banking transaction data has additional
  structure (merchant categories, cross-border patterns, device/IP
  signals) this project doesn't model.
- **Offline RL training.** The DQN is trained and evaluated on a static
  historical split, not in a live, continuously-updating loop with real
  analyst feedback — a production deployment would need online or
  periodic retraining, which `run_phase4_rl.py` and the drift detector
  are built to support but don't fully automate yet.
- **Single-institution scope.** The system reasons about one transaction
  stream at a time; it doesn't yet model cross-institution or network-level
  laundering patterns (e.g. layering across multiple accounts/banks).
  Fields like `nameOrig`/`nameDest` are used for the burst-detection rule
  (R2) but not for deeper graph-based analysis, which is a natural
  extension of this codebase.
- **Threshold sensitivity.** Both the static-threshold baseline and the
  RL policy are sensitive to the reward magnitudes in `src/config.py`;
  changing `MISSED_FRAUD_COST` or the RL reward values changes the
  recall/workload trade-off, and should always be re-validated against
  the fraud-recall floor before deployment.
- **Explainability is template-based, not causal.** `explainability.py`
  produces structured, audit-readable reasoning from the state features
  and rule triggers — it's not a formal causal attribution (e.g. SHAP)
  over the underlying model. Adding that is a natural next step for
  deeper regulatory scrutiny.
